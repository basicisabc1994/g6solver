# G6 0.3.0: the first beta

Beta. Individual capabilities have been tested; general application-level improvements have not yet been established.

0.3.0 turns G6 from one review tool into a harness a coding agent works inside: it is told when to call G6, a refused
call says how to repair it, the person's consent stands before any cloud model, and in Claude Code the work is checked
when the agent says it is finished. G6's MCP server, the surface of record, goes from 20 tools in 0.2.0 to 70.

Merging stays the person's decision.

## What is new

### Checking the work when the agent stops

- **A model-free review at every stop.** G6's plugin for Claude Code (`/plugin marketplace add basicisabc1994/g6solver`,
  then `/plugin install g6@g6solver`) has a Stop hook. When the agent finishes and Python files have changed, the hook
  runs G6's patch review with no model: it runs the tests that touch the changed modules inside an operating-system
  boundary, and looks for weakened tests. It shows you the report: which checks ran, what was skipped and why, and the
  time taken. With no reviewer approved, it shows the report and ends the turn.
- **The end-of-task card.** The report opens with five lines: checked, caught, repaired, not checked, and needs you.
  Each number on it comes from an event in G6's local workflow record for the task, and the card names those events.
  With the record off, or nothing recorded for the task, the card says so and gives no numbers. The same card is in
  `g6_review_patch`'s reply and in the loop's report.
- **The reviewer loop is an opt-in extra.** It spends the person's own sign-in, so it runs only after they add
  `G6_LOOP_CRITIC=codex` (or, for the scouts' loop, `G6_LLM_PROVIDER=claude_code`) to their key file, `~/.g6/.env`. A
  line set in the agent's environment does not count. Codex then reads the patch without the agent's reasoning (a
  reviewer from another model family when the agent is Claude Code's Claude, not when the agent is Codex) and must
  state a rule, its reasons and a test.
- **The parent rule.** G6 runs each reviewer test on the parent commit and on the patch, inside the boundary. A test
  counts as a finding only when it fails on both. A test that fails only on the patch, or whose parent run is
  unavailable, is shown to you as a note with the case and the reason, and is not sent back to the agent. A finding
  goes back to the agent in the same session, up to three repairs. The loop's report ends in one word: `clean`,
  `fixed`, `contested`, `open` or `untested`. A review that reproduces nothing only means this reviewer found no failure
  it could show.
- **Other clients** run the same loop one step at a time with `g6_review_until_clean`.

### Reviewing a patch

- **Behaviour questions** (`g6_confirm_behaviour`): where a task leaves behaviour undecided, G6 asks the person one
  question in the client's own dialog. A confirmed answer becomes a check that every later review of the task runs.
- **Before the work** (`g6_premortem`): what done would mean and how the task can fail, with no model call.
- **Missions** (`g6_mission_*`, six tools): a standard of done fixed before the work and confirmed by the person,
  then the patch checked against it.
- **The change map.** A review now returns an advisory map of which collected tests reach the changed code. It is a
  lead for the agent, never evidence and never a decision.

### Knowing which G6 step fits, and repairing refused calls

- The server tells a connected agent when to call G6, and in Claude Code a task starts with a hint of at most 60 words
  (`G6_HINTS=off` turns it off).
- `g6_select` picks the next G6 step from G6's own catalogue, and offers discovery when nothing fits.
- A refused reply carries a `repair` block that says what to fix and who fixes it. When only the person can resolve a
  refusal, the reply tells the agent to ask them and stop.
- The isolation refusal names the folder that needs the one-time access grant, and `g6 doctor` checks the repository
  it runs in as well as this computer.
- The `using-g6` skill routes to every tool that ships, opens in under 800 words and links its detail by route.
- `g6 setup --client codex` offers G6's instructions as a block in `AGENTS.md`, written only if the person accepts.

### Consent and model use

- **Consent before any cloud model** (`g6_cloud_grant`, `g6_cloud_grants`, `g6_cloud_revoke`, `g6_disclosures`).
  No user data reaches a cloud model unless the person granted it, per source and per provider, in the client's own
  dialog. One check covers G6's own model calls, `g6_invoke`, `g6 invoke`, the Python `g6.invoke`, the cognitive
  bridge and the self-improvement loop's sessions. A disclosure record says what was sent.
- **Model overrides** (`g6_agentic_run`): after a declared limit or failure in a component, a model can stand in for
  that part, after the person agrees in the dialog. The reply names the model and keeps the original answer beside
  it.
- **Allowances** (`g6_allowances`): both providers' quota windows and advisory pacing. Unknown or stale readings
  never recommend more use.
- Patch review still makes no model call unless the caller turns one on.

### Learning from failures

- **The library of learned checking methods** (12 new tools). `g6_failure_record` records a failure; `g6_distill_start` and
  `g6_distill_job` turn cases that a confined oracle run labels into candidate checking methods; `g6_library` lists
  them with their history; `g6_library_decide` asks the person to demote or withdraw one. A method gains authority only
  through a held-out acceptance gate that no method or request can change, and it reports a measured precision, never
  a guarantee. A method's silence never passes a requirement.
- **G6's model of itself** (`g6_self_model`, `g6_simulate`, `g6_extend`): measured state, forecasts that stay unknown
  without recorded earlier actions, and capability requests that grant nothing.
- **The research runner** (`g6_research_*`): off. It refuses until the owner turns research authority on and a host
  runner is attached.
- **The self-improvement loop over MCP** (`g6_improve_*`, six tools). The person agrees in the dialog to each start,
  enrolment, resume and demotion; the stop needs no dialog. The loop changes only its own workspace and pushes
  nothing.

### Context and records

- **The Context Engine** (`g6_knowledge_*`, 11 tools): a local index of folders under the roots the person lists in
  `G6_KNOWLEDGE_ROOTS`, searched by words, each passage cited. Adding a folder asks the person to accept a preview.
  The meaning route is not in this release.
- **The workflow record** (`g6_feedback`, `g6_suggestion_decide`, `g6_workflow_correct`, `_delete`, `_export`): on by
  default; `G6_WORKFLOW_RECORD=off`, set where the server is registered, turns it off. Its view in review replies stays
  off unless the person names a level in `G6_WORKFLOW_VIEW` or sets `G6_WORKFLOW_RECORD=on`. An export also writes
  `RECORD.md`, a readable copy, beside `inspection.json`. Deletion by run or task removes every store's entries for
  it.

## Fixed before release

Each was a must-close finding on code that ships, and each is covered by the test file named with it.

- **The MCP server did not start under a real client on Windows** when the client's piped input was not UTF-8. G6 now
  reads its own standard input and owns its writer: a reply counts only once its whole line was written. Covered by
  `tests/_review_wcfu3r4/test_default_text_encoding.py`.
- **Caller-supplied metadata could overwrite fields G6 writes as evidence**, such as a caveat's refusal reason or a
  child job's seed. It no longer can. Covered by `tests/evidence/test_caller_extra_states_no_g6_field.py`.
- **The Python API `g6.invoke`** now goes through the same consent check as every other door. Covered by
  `tests/core/test_consent_python_door.py`.
- **A claim premise made only of invisible characters** (combining marks, variation selectors, Hangul fillers) was
  admitted as a premise. A premise now needs visible text. Covered by
  `tests/_review_unkprem4/test_invisible_premises.py`.
- **The storage check followed a mount point to a named pipe** and connected to it before refusing. It now refuses a
  link or mount point to a device or network target before following it. Covered by
  `tests/core/test_storage_device_link.py`.
- **The skill's safety census dropped a bold caption** with no authority keyword, so a visible qualification could
  disappear and a weakened rule still pass. It now keeps the caption. Covered by
  `tests/skills/test_census_caption_regression.py`.
- **Deeply nested JSON** read through the sharing check, or in a saved code configuration, ended in a bare error
  instead of G6's refusal. It now ends in the refusal. The JSON readers this release adds, in distillation,
  self-training, the skill corpus and the test runner, also go through G6's guarded decoder. Covered by
  `tests/s16r3/test_reply_followup.py` and `tests/rfu_r3/test_decoder_routing.py`.
- **A network-share path** (`\\host\share` and its other spellings) given as a repository was checked on disk before
  it was refused, which on Windows opens the share. It is now refused on its words, before G6 touches it. Covered by
  `tests/workforce/test_repo_tests_network_paths.py`.
- **A provider's error text could pass for a consent refusal**, and a review refused after a request went out could
  be reported as not sent. G6 now reads a consent refusal from its own record, and says "not sent" only when no
  request was counted. Covered by `tests/harness/test_completion_consent_signals.py`.
- **The Stop hook tested nothing by default**, while the plugin's README said a reviewer reads the patch. It now runs
  the model-free review by default, and the README says what runs. Covered by
  `tests/harness/test_completion_stop_default_review.py` and, for the parent rule,
  `tests/harness/test_completion_parent_rule.py`.
- **The isolation refusal was garbled** by the filter that removes setup commands from agent-facing text. It now reads
  cleanly. Covered by `tests/core/test_isolation_refusal_for_agent.py`.

## Install and first use

You need Python 3.12 or 3.13, git, and Claude Code or Codex. Run these yourself, in a terminal:

```bash
git clone https://github.com/basicisabc1994/g6solver && cd g6solver
python -m venv --copies .venv                           # G6's own environment, with a copy of Python
source .venv/bin/activate                               # PowerShell: .venv\Scripts\Activate.ps1
pip install ".[all]"
g6 doctor                                               # read-only: what this computer offers G6
g6 setup --client claude --allow patch_review.review    # or --client codex; give --client twice for both
```

On Windows, run the one-time access grant that `g6 doctor` prints. `g6 doctor` also checks the repository it runs in,
so run it once in each repository you want reviewed. If it warns that a confined test cannot run git, it also prints
one read-attributes-only grant for each folder above the temporary folder; G6 never runs these grants itself.

Restart the client. In a Python repository, ask your agent for a change, then ask it to review the change with G6
before it says the task is done. It calls `g6_review_patch`, polls `metaharness_job`, and shows you the reply's
`assessment.report` as it is. The outcome is one of: test integrity compromised, defect detected, insufficient
evidence, or supported within scope.

The first review in a repository G6 has not seen asks you, in the client's dialog, to share that repository. After you
accept, the agent runs the review again.

In Claude Code, start Claude Code with G6's environment active (the plugin's hooks use the `python` on its `PATH`)
and install the plugin as above. The Stop hook then reviews each Python change with no model. For the reviewer loop,
add `G6_LOOP_CRITIC=codex` to `~/.g6/.env`.

If you have an entry from 0.2.0, setup leaves it and stops: remove it with `claude mcp remove --scope user g6` (or
`codex mcp remove g6`) and run `g6 setup` again.

## Supported platforms

- **Linux** with bubblewrap (install the `bubblewrap` package): G6 confines the code it runs.
- **Windows**, after the one-time access grant that `g6 doctor` prints: G6 confines the code it runs in an
  AppContainer. Hosted Windows CI runners cannot create one, so Windows patch review was exercised on a local machine.
  Tests that run git fail inside the AppContainer until the person runs the read-attributes-only grants that
  `g6 doctor` prints, and until then G6 reports them as failing checks; see the known limits.
- **macOS is out of scope for 0.3.0.** G6 has no boundary there: patch review and the completion loop refuse, and
  other tools refuse untrusted code unless the person allows it once, in which case it runs with their own rights.
  This is a known limit.

Patch review and the completion loop test Python repositories with pytest only.

## Deferred to 0.3.1

These were built and are still in review, so they are not in 0.3.0:

- `g6_record`, a tool that reads back the record of what G6 checked;
- evidence custody, and a record of which code each test depended on;
- which tests a change touches, with the ones not reached named;
- template behaviour checks bound to methods;
- grounding of claims with LangExtract;
- clarity reports, intent candidates and typed test-output parsers;
- unknown costs in graph reasoning, and discriminating diagnosis;
- typed completion-loop records;
- tool families with short descriptions and describe on demand;
- learning from recorded outcomes, selection by meaning, and a model by default through the person's own sign-in.

## What one person saw using it

This is n=1 dogfooding: one person, one Windows machine, ten patches from this release's own work. It is not a study,
and no claim rests on it.

- **Before the one-time access grant**, no review could run: each of the ten was refused for isolation
  (`G6_E_ISOLATION_UNAVAILABLE`).
- **With the grant**, the bar of three catches set for this beta was not met. G6 alone made one catch, on a branch
  deferred to 0.3.1. With an agent's proposed checks, it made one more, on code that ships.
- **False alarms.** G6 alone reported defects on correct patches. Five came from tests that fail only inside its
  Windows sandbox, where git cannot run (the first known limit below). Two more flagged test edits the change needed
  as weakened tests.

## Not yet measured

No claim in this release rests on these. They have not run:

- **Fresh-session routing trials**: whether Claude Code and Codex, in fresh sessions, call G6 at the moment it could
  help without being told to. Before any session ran, the study's pins were re-recorded by dated amendments for the
  review, learn, question and workflow routes, and three development tasks were added for learn.
- **The distillation study**: three arms (static checks, reflection only, compiled checks) on weakened tests. Two
  pilots stopped before a label could be read, so nothing is known about unseen-failure detection, transfer or reuse.

The bars set for this beta were a net gain of at least one on paired moment-of-need tasks with hidden checks, or at
least three catches in dogfooding. The first has not been measured; the second was not met. Also not yet measured:
the completion loop beyond seven training bugs, the self-improvement loop over an unattended week, allowance pacing
against real provider windows, consent in a real client's dialog, the Context Engine's retrieval quality, the
workflow record's suggestions, and behaviour questions with real people. A passing test establishes only the
behaviour it covers.

## Known limits

205 known limits ship, each with its id in [KNOWN_LIMITS.md](KNOWN_LIMITS.md), beside five platform and scope lines.
Each fails in the safe direction, needs code already running in G6's own process or another program running as the
same user, is a narrow platform edge that ends in an error, is a narrowed race, or sits in repository tooling. The
largest groups are the Context Engine (27), tool routing and its instrument (27), the completion and self-improvement
loops (25) and the component door and cognitive bridge (22). For 79 of them a repair has landed that no fresh review
has re-checked.

Other limits to know first:

- **Windows and git.** On Windows, tests that run git fail inside G6's sandbox, because the sandbox cannot read the
  folders above the temporary folder. `g6 doctor` warns of this and prints a one-time read-attributes-only grant for
  each such folder. Until the person runs them, such a failure is still reported as `defect_detected`, and the reply
  quotes the failure's own line (masked, at most 300 characters) so the cause can be seen. A separate outcome for
  failures of the computer rather than the patch is planned for 0.3.1.
- **The patch runs where its tests run.** The patch's own code runs in pytest's process, in the repository's own
  environment: a patch written to defeat the checks can make them report a pass, and G6 does not catch that.
- **What an outcome means.** Supported within scope means every stated requirement passed its stated checks; it does
  not show that the patch does everything the task needs.
- **A trusted host.** Local settings, hooks and G6's state can be changed by anything running as the same user.
- **G6's own environment.** Install G6 with `python -m venv --copies`: on Linux, G6 cannot yet tell its own Python
  from a project environment linked to the same one, and refuses to review then.
