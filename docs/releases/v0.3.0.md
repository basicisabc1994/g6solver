# v0.3.0 preparation — not published

This note goes with the draft pull request that brings the 0.3 integration line (`claude/integrate-0.3`) into `main`.
Nothing here is tagged, released or published, and v0.1.0 stays immutable. Merging, tagging, publishing to PyPI and
deploying the site are the owner's steps.

Status: early alpha. Individual capabilities have been tested; general application-level improvements have not yet
been established.

## What 0.3.0 adds

The MCP server goes from 20 tools to 56 (counted from `g6.mcp.build_server()`); the core library keeps 38 components,
20 of them reachable over MCP.

- **Consent before any cloud model** (`g6_cloud_grant`, `g6_cloud_grants`, `g6_cloud_revoke`, `g6_disclosures`). No
  user data reaches a cloud model unless the person granted it, per source and per provider, in the client's own
  dialog. Without a grant the work stays local, or the result is withheld. The check is the same one for every path
  that can reach a model: G6's own model calls, the MCP and CLI door (`g6_invoke`, `g6 invoke`), the cognitive bridge,
  and the self-improvement loop's Claude Code and Codex sessions. An inventory test holds that list, and a disclosure
  record says what was sent. A revoked grant stops a caller that was kept from an earlier call. One path, the Python
  API `g6.invoke`, lives in a certificate-bound file and is put through the check at the issuance window (below).
- **The self-improvement loop, over MCP** (`g6_improve_start`, `_stop`, `_status`, `_enrol`, `_resume`, `_demote`).
  A start, an enrolment, a resume and a demotion are each agreed by a person in the client's dialog; status only
  reads. The stop needs no dialog and no permission. A frozen file that changes, a provider refusal, a missing consent
  grant or a record that cannot be written stops the loop and is kept as a safety stop for a person to resume. Outside
  a loop tick, G6's own Claude Code and Codex reviewers start after the consent check alone.
- **Allowances** (`g6_allowances`): both providers' quota windows and advisory pacing. Unknown, stale or unbound
  readings never recommend more use.
- **Behaviour questions** (`g6_confirm_behaviour`): one question about a task, answered in the client's dialog. A
  confirmed answer becomes a check that every later patch review of the task runs. It runs in G6's own fresh
  interpreter, not under the repository's pytest setup. It is bound to the import roots and file it was confirmed
  from: a patch that edits the function is checked, while one that moves it, or a caller who changes the import path,
  is refused. The repository's own module code still runs inside that interpreter and can shape its own observed
  outcome (`docs/BEHAVIOUR_QUESTIONS.md`).
- **Missions and review** (`g6_mission_*`, `g6_premortem`, `g6_review_until_clean`): a coding task carried to an
  evidenced result, with the reviewer loop that ends clean or says why not.
- **The Context Engine** (`g6_knowledge_*`, 11 tools): knowledge search over folders the person names in
  `G6_KNOWLEDGE_ROOTS`. Adding a source asks the person to accept a preview in the dialog.
- **The workflow record** (`g6_feedback`, `g6_suggestion_decide`, `g6_workflow_correct`, `_delete`, `_export`): off
  unless `G6_WORKFLOW_RECORD=on` is set where the server is registered. With it off nothing is kept but the inspection
  file and receipts. Deletion by run or task removes every store's entries for it.
- **Routing**: the `using-g6` skill routes to every tool that ships, held by an inventory test, with routing tasks for
  each route.
- **The cognitive bridge** as a core component. Its constructor admits only plain names and state, so no inherited
  output can publish a caller's claim.
- **Tests cannot start a real host.** The suite points Claude Code and Codex at a program that does not exist, so a
  test that fakes a host incorrectly fails instead of reaching an installed CLI.

## Must-close findings

Every must-close finding on the code that ships is closed on this line, or its code stays out:

- 73 are closed with the reviewer's own test passing on the integration line.
- 6 are closed with a product test. In each, the reviewer's test fixture cannot reach its finding on the fixed code
  (it relied on a hook or a behaviour the fix removed). The product test reproduces the same scenario and passes.
- 1 waits for the certificate issuance window (`review-efu3#4`, a certificate-bound writer), as does `g6.invoke`'s
  consent path.
- 13 belong to code that is not in 0.3.0: the study's execution and capture code, and section 15.

Each finding with its evidence is in [`v0.3.0-ledger.tsv`](v0.3.0-ledger.tsv).

## Known limits

[`v0.3.0-known-limits.md`](v0.3.0-known-limits.md) lists 141 reproduced findings, in 30 changes, that ship as known
limits. Each one fails in the safe direction (G6 refuses, withholds or reports less), needs code already running in
G6's own process, is a narrow platform edge ending in an error, is a narrowed race, or needs a certificate-bound file.
The largest groups are the Context Engine (26), routing and the paired evaluator (26), the PR #8 follow-ups (18) and
the workflow record (10).

Also known, beyond the ledger:

- On the Windows machine this line was tested on, confirmed behaviour checks end `insufficient_evidence` or `not_run`
  in `tests/harness/test_confirmed_enforcement.py` (4) and `test_confirmed_evidence_bound.py` (11). They fail the same
  way before this line's changes, and have not yet been run on Linux.
- The agent runtimes (`agent_claude`, `agent_codex`) look up their program before the consent check, so an
  ungranted run on a machine without the program says the program is missing, not that consent is needed. Nothing
  is sent either way. G6's own host calls decide consent first.
- About 30 host tests that name no grant fail the same way before and after this line's changes (they need a consent
  fixture), and one (`test_refufu2r1_finding_1`) is refused for consent before the check it is about.
- A tool argument holding a lone surrogate character is refused by the MCP layer with a generic tool error, not G6's
  own refusal envelope. Nothing is sent.
- The routing trial's list of dialog tools (`validation/routing/run.py`, `DIALOG_TOOLS`) does not yet include the
  newer dialog tools, so a routing trial would not count their calls as questions.

## Not yet measured

These parts ship switched on and have not had their measurement run. A passing test establishes only the behaviour it
covers; none of these is claimed to improve outcomes:

- the self-improvement loop (an unattended week; adoption of anything it proposes);
- allowance pacing against real provider windows;
- consent in a real client's dialog, across Claude Code and Codex;
- the `using-g6` routing (no routing session has been run with the new skill text and tasks);
- the Context Engine's retrieval quality;
- the workflow record's suggestions;
- behaviour questions with real people.

## Before the tag

- One certificate issuance window: the certificate-bound changes listed in the ledger (`needs_bound_file`), including
  `review-efu3#4`, the consent path of `g6.invoke`, and caller extras never overwriting an authoritative evidence
  field. Then the certificates are renewed through their normal checks.
- The seven release gates:

| Gate | Required evidence |
|---|---|
| Software | Split regression suites on Linux and Windows, built-wheel install smoke, supported dependency versions |
| Isolation | Windows and Linux adversarial probes; skips do not count as passes |
| Client consent | The owner grants, declines and revokes in Claude Code and in Codex |
| Usability | A fresh developer gets from install to a first useful result unaided |
| Utility | A first real task where G6's review changed the outcome, recorded |
| Broader usability | The same on a second client and platform |
| Artifacts | Wheel, catalogue, failure map and certificates match the tagged commit |
