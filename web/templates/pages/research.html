Where G6 gained, and where it did not.

AI is usually judged by public benchmarks, and a high score there often fails to carry over to real work. So G6 never takes a score on trust: every change it makes is tested on tasks held out from it.

Every study here asks one question: how much better does the same model do inside a harness than on its own? It counts every study run, the earliest included, and says which part of G6 did the work. Together they are a worked example, built to show what the system can do; on your own work, results will vary with the task and the data you have. How to read them

A worked example

Claude Code on real bugs, with a review loop and without

We set out to measure whether G6 makes a coding agent right more often than Claude Code alone, on real bugs neither had seen. We registered every test and its bar before running it.

{{ c.label }}

How it was measured

Real bugs Bugs reported in well-known Python projects, each fixed and merged by the project's maintainers. In each run Claude Code, on {{ c.model }}, got the issue and the code as it was before the fix, and wrote a patch. Claude Code alone ran as many times as each loop, on every bug.
Two truths Tests the agent never saw scored every patch afterwards: the maintainers' own tests, and amended tests, which drop any name, message or format the maintainers' tests require and the issue never states.
A fixed rule, by bug A loop shows a gain only if it passes more runs than Claude Code alone, and than Claude Code given the issue's discussion where that ran, and an exact one-sided sign test over the bugs it does better and worse on gives p below {{ c.rule.alpha }}. That takes at least {{ c.rule.min_wins }} bugs better and none worse. The rule was first written over pairs of runs. It is read over bugs, which is stricter, because two runs of one bug are not independent.
Does the issue decide the fix? An auditor that ran no task and saw no run read each issue blind, with the tests its fix changed, and said whether the issue states enough to determine the fix. Where models from {{ c.audit.families }} families made that call independently, on {{ c.audit.issues }} further issues, they agreed on {{ c.audit.agreed }}.
Power How often a study of a given size would meet the rule was estimated by resampling the recorded bugs, each with its own runs.

The loops

{{ c.labels.M9 }} Before any patch, separate sessions read the issue and the code and write tests for the fix. The patch is run against them and sent back for repair, and {{ c.reviewer }} reviews it once. Built from G6's parts.
{{ c.labels.K1 }} {{ c.reviewer }}, from another model family, reviews the patch and must write a test that fails on it. Claude Code repairs in the same session, and a fresh review reads the new patch, up to {{ c.max_repairs }} repairs.
{{ c.labels.V4 }} The review loop, with one test written from the issue and the code before the agent starts, which fails while the reported symptom is still there.

Every loop also gave Claude Code the issue's discussion. The review loops ran in the study's own code, with none of G6's at run time.

The limits of self-improvement, and where checking helps

Tuning fitted what it was tuned on Both loops led Claude Code alone on the bugs they were tuned on. On unseen bugs, even in the same repositories, that lead shrank or turned into a loss, and no comparison met the rule (the tables above). When G6's own self-improvement loop tuned the reviewer on {{ c.three.tuning_cases }} recorded cases, with no change written by hand, its best candidate lost to the reviewer it started from on cases held out from it, {{ c.three.held_out.wins }} to {{ c.three.held_out.losses }}, and G6's gate refused it.

How to read these results

A worked example: these studies show where a harness around the same model gained, on public tasks and real bugs, and where it did not. They are not a forecast for yours.

What they are The local-model studies are Claude Code working with G6 on one 8-billion-parameter local model ({{ facts.model }}) and public task sets. Every score there is on fresh tasks that no tuning step saw, against the same model alone. One adaptation study was registered before it ran; the development rounds were not, and the method was improved between them. Each task set's winning option is picked after the fact from the options measured. The coding study is Claude Code itself, on {{ coding.model }}, fixing reported bugs in well-known Python projects, alone and inside review loops, each run scored by tests the agent never saw; its scores on the bugs the loops were tuned on are shown as such, and every test and its bar was registered before it ran.
What they show
  • Where a model fails in a systematic way, G6 can engineer a large gain in minutes, on the same model: {{ facts.largest.0 }} went from {{ facts.largest.1 }} to {{ facts.largest.2 }} of {{ facts.per_dataset }} in the registered study.
  • The gate decides on evidence, whoever proposes a change: random changes put through it were approved when they won on held-out tasks and refused when they did not. G6's own reflective tuning found more than random search overall ({{ facts.total.D }} against {{ facts.total.F }} of {{ facts.n }} tasks in the registered study), but not on every task set.
  • The winning approach follows the task's structure: one instruction where a single change fixes the main failure, prebuilt components where the gain needs layers such as labelled examples or test-and-repair. The registered study supports G6's Swiss cheese design of prebuilt failure layers.
  • The two modes are alternatives, not a stack: in development round {{ both.round }}, self-tuning that started from every prebuilt component had no change approved, and on {{ both.worst.dataset }} every component on did worse than the model alone. Which mode wins depends on the task.
  • A small model can be bootstrapped through its harness: larger models engineer it, and the small model runs inside it alone, with no weights changed.
  • On real bugs, the loops around Claude Code did well on the bugs they were tuned on and showed no significant uplift over Claude Code alone on unseen ones: no registered test there met its fixed rule. Where the issue fully states the fix, checking moved a few runs the right way; where it does not, only a person or the maintainers' tests could supply what was missing.
What they do not show How G6 does with other models or other coding agents, on your tasks, or that a harness tuned for one task set helps another. Nor do they show that a harness adds knowledge a model lacks: much of each gain is the model doing what it can already do, once it is asked the right way. With 100 tasks per set, a difference of a few tasks can be chance; the large gains are not. The earlier benchmark studies were audited, not run again.
Why results vary G6 can only engineer what your checks and examples can measure: it needs about 30 or more held-out examples with known answers before it will approve a change. Gains are largest where errors are systematic and a harness change addresses them, and smallest where the model is already near its ceiling or lacks the knowledge a task needs.

How every component meets the four hard problems of self-improvement

ProblemWhat every component does about it
Turning weak or partial evidence into reliable learning signalsEvery failure it catches is written to the run ledger as a labelled incident with its evidence and its failure mode: the input the meta-harness and the theory loop learn from.
Evaluators the adapting system cannot influenceIts checks are its own code, pinned by digest, or an outside tool (tests, a prover, a renderer), never written or tuned by the model being checked.
Transfer of learned safeguards to unseen task familiesA safeguard is bound to a failure mode, not to a task, so it applies wherever that mode can occur; its catch rate is measured on task families it was not built on.
Enough held-out examples to tell a real improvement from noiseIts catch rate and false-alarm rate are judged by G6's sequential test, which says how many more cases it needs instead of guessing.
