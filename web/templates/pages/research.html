Where G6 gained, and where it did not.

AI is usually judged by public benchmarks, and a high score there often fails to carry over to real work. So G6 never takes a score on trust: every change it makes is tested on tasks held out from it.

Every study here asks one question: how much better does the same model do inside a harness than on its own? It counts every study run, the earliest included, and says which part of G6 did the work. Together they are a worked example, built to show what the system can do; on your own work, results will vary with the task and the data you have. How to read them

A worked example

Claude Code on real bugs, with a review loop and without

The study asked whether a harness improved on training bugs beats Claude Code alone on bugs it never saw. In each run Claude Code, on {{ c.model }}, was asked to fix a reported bug in a well-known Python project, and tests the agent never saw scored the run afterwards. The review loop did well on the bugs it was tuned on; on unseen bugs it showed no significant uplift, in any of three stages.

{{ c.label }} Every run has two scores: the maintainers' own tests, and amended tests, which drop any name, message or format the maintainers' tests require and the issue never states.

  • The review loop on the bugs it was tuned on: {{ t.passed.maintainers.K1 }} of {{ t.runs }} runs on the maintainers' tests and {{ t.passed.amended.K1 }} of {{ t.runs }} on the amended tests, at ${{ t.cost.K1 }} a run against the scout loop's ${{ t.cost.M9 }}.   • On new repositories, direction only: in stage 2 the review loop was never behind Claude Code alone on any bug, {{ two.passed.maintainers.K1 }} against {{ two.passed.maintainers.A }} and {{ two.passed.amended.K1 }} against {{ two.passed.amended.A }} of {{ two.runs }}, and on {{ two.one_bug.bug }} every arm with a reviewer passed while every arm without one failed.
  • Finding where G6's own code breaks: the same loop, with {{ own.reviewer }} as the reviewer, found {{ own.total }} defects in {{ own.count }} branches of G6's own code, each counted only when a test that failed before the fix reproduced it (the table below).
  • Diagnosing the study itself: G6's root-cause analysis of its own refusal in stage 3 did not bear out the cause a person had named by hand, and named three others (below). Two raters, labelling {{ c.blind_labels.patches }} failed patches blind, agreed on {{ c.blind_labels.agreed }} failures and put {{ c.blind_labels.within_reach }} of them within reach of evidence an engineer has (reading the surrounding code, or running the issue's own example) and {{ c.blind_labels.out_of_reach }} out of reach of anything short of the maintainers' intent. What did not

  • No significant uplift over Claude Code alone on unseen bugs, in any of the three stages. The {{ c.rule.target_pct }}% target was met in none: the best a judged loop did on unseen bugs was the {{ c.best.arm|lower }}'s {{ c.best.pct }}%, on stage {{ c.best.stage }}'s {{ c.best.score }}.
  • The reviewer's first verdict did not carry: on unseen bugs it agreed with the truth on {{ c.first_verdict.unseen.0 }} of {{ c.first_verdict.unseen.1 }} runs, against {{ c.first_verdict.training.0 }} of {{ c.first_verdict.training.1 }} on the bugs it was tuned on.
  • Picking the right patch: a blind reader choosing the right one among {{ c.blind_reader.choices }} did no better than chance with {{ c.reviewer }}, and two readers agreeing did no better.
  • Review loops on G6's own code seldom reach an empty review: {{ own.clean }} branch{{ own.clean|pluralize:"es" }} of {{ own.count }} did; {{ own.ran_out }} ran out of repairs with {{ own.open }} findings still open, and {{ own.in_loop }} {{ own.in_loop|pluralize:"is,are" }} still in {{ own.in_loop|pluralize:"its loop,their loops" }}.

Why

The reviewer's feedback does not carry to unseen bugs Its first verdict agreed with the truth on {{ c.first_verdict.training.0 }} of {{ c.first_verdict.training.1 }} runs on the bugs it was tuned on and {{ c.first_verdict.unseen.0 }} of {{ c.first_verdict.unseen.1 }} on unseen ones. The review loop's lead over Claude Code alone on the maintainers' tests went from {{ t.lead }} points in training to {{ one.lead }} in stage 1 and {{ two.lead }} in stage 2.
Little headroom, and too few bugs On {{ two.same_bugs }} of stage 2's {{ two.bugs }} bugs Claude Code alone and the review loop scored the same, so only {{ two.differing }} pairs of runs could differ. Even with all {{ two.differing }} going one way, a sign test puts that at p = {{ two.best_p }}, short of the {{ c.rule.alpha }} the rule needs.
Failures that need the maintainers' intent {{ c.blind_labels.out_of_reach }} of the {{ c.blind_labels.agreed }} failures the two raters agreed on were out of reach of anything short of the maintainers' intent.
A self-improvement step whose edits are too narrow In stage 3 every candidate changed only the reviewer's wording or its examples. G6's root-cause analysis of that round, run as plain code on its records afterwards, names that edit space as too narrow, and two more causes: the winner moved where the reviewer draws its line rather than reading better (all {{ c.diagnosis.threshold_move.wins_all_on_right_patches }} held-out cases it won were right patches, and all {{ c.diagnosis.threshold_move.losses_all_on_wrong_patches }} it lost were wrong ones), and it won its race only {{ c.diagnosis.race_noise.race_won.0 }} to {{ c.diagnosis.race_noise.race_won.1 }}, too close to tell from chance, and a candidate tied with it was dropped. It did not bear out the cause a person had named by hand, that the tuning and held-out cases were mixed differently: the reviewer's failures were false alarms {{ c.diagnosis.tuned }}% of the time on the tuning cases and {{ c.diagnosis.held }}% on the held-out ones, {{ c.diagnosis.apart }} points apart, short of the {{ c.diagnosis.skew_line_points }} points the analysis takes as a skew.

This supports the Swiss cheese design G6 is built on: each prebuilt component is a layer against one kind of failure, several are needed where one alone is not enough, and the structure of the task decides which layers matter. It is why G6 offers both modes, and why it tests both on your own examples.

Development round {{ both.round }} measured the two modes together, and they did not stack: self-tuning that started from every prebuilt component had {% if both.approved_from_components %}{{ both.approved_from_components }} change{{ both.approved_from_components|pluralize }} approved{% else %}no change approved on any of its {{ both.datasets }} task sets{% endif %}, and on {{ both.worst.dataset }} every component on did worse than the model alone ({{ both.worst.components }} against {{ both.worst.alone }} of {{ both.worst.n }}; {{ both.worst.lost }} tasks lost, {{ both.worst.gained }} gained). There a check asks every answer a second time with its own fixed question, so no instruction upstream could change the final label: one layer can mask another. The modes are alternatives, chosen per task on held-out evidence, not layers to switch on all at once.

How to read these results

A worked example: these studies show where a harness around the same model gained, on public tasks and real bugs, and where it did not. They are not a forecast for yours.

What they are The local-model studies are Claude Code working with G6 on one 8-billion-parameter local model ({{ facts.model }}) and public task sets. Every score there is on fresh tasks that no tuning step saw, against the same model alone. One adaptation study was registered before it ran; the development rounds were not, and the method was improved between them. Each task set's winning option is picked after the fact from the options measured. The coding study is Claude Code itself, on {{ coding.model }}, fixing reported bugs in well-known Python projects, alone and inside review loops, each run scored by tests the agent never saw; its scores on the bugs the loops were tuned on are shown as such, and its rule was fixed before its stages ran.
What they show
  • Where a model fails in a systematic way, G6 can engineer a large gain in minutes, on the same model: {{ facts.largest.0 }} went from {{ facts.largest.1 }} to {{ facts.largest.2 }} of {{ facts.per_dataset }} in the registered study.
  • The gate decides on evidence, whoever proposes a change: random changes put through it were approved when they won on held-out tasks and refused when they did not. G6's own reflective tuning found more than random search overall ({{ facts.total.D }} against {{ facts.total.F }} of {{ facts.n }} tasks in the registered study), but not on every task set.
  • The winning approach follows the task's structure: one instruction where a single change fixes the main failure, prebuilt components where the gain needs layers such as labelled examples or test-and-repair. The registered study supports G6's Swiss cheese design of prebuilt failure layers.
  • The two modes are alternatives, not a stack: in development round {{ both.round }}, self-tuning that started from every prebuilt component had no change approved, and on {{ both.worst.dataset }} every component on did worse than the model alone. Which mode wins depends on the task.
  • A small model can be bootstrapped through its harness: larger models engineer it, and the small model runs inside it alone, with no weights changed.
  • On real bugs, a review loop around Claude Code did well on the bugs it was tuned on and showed no significant uplift over Claude Code alone on unseen ones: on bugs from repositories never used in training it passed {{ coding.two.passed.maintainers.K1 }} of {{ coding.two.runs }} runs against {{ coding.two.passed.maintainers.A }}, direction only.
What they do not show How G6 does with other models or other coding agents, on your tasks, or that a harness tuned for one task set helps another. Nor do they show that a harness adds knowledge a model lacks: much of each gain is the model doing what it can already do, once it is asked the right way. With 100 tasks per set, a difference of a few tasks can be chance; the large gains are not. The earlier benchmark studies were audited, not run again.
Why results vary G6 can only engineer what your checks and examples can measure: it needs about 30 or more held-out examples with known answers before it will approve a change. Gains are largest where errors are systematic and a harness change addresses them, and smallest where the model is already near its ceiling or lacks the knowledge a task needs.

How every component meets the four hard problems of self-improvement

ProblemWhat every component does about it
Turning weak or partial evidence into reliable learning signalsEvery failure it catches is written to the run ledger as a labelled incident with its evidence and its failure mode: the input the meta-harness and the theory loop learn from.
Evaluators the adapting system cannot influenceIts checks are its own code, pinned by digest, or an outside tool (tests, a prover, a renderer), never written or tuned by the model being checked.
Transfer of learned safeguards to unseen task familiesA safeguard is bound to a failure mode, not to a task, so it applies wherever that mode can occur; its catch rate is measured on task families it was not built on.
Enough held-out examples to tell a real improvement from noiseIts catch rate and false-alarm rate are judged by G6's sequential test, which says how many more cases it needs instead of guessing.

The papers are design rationale: their proofs are not machine-checked, and none is cited as evidence.
